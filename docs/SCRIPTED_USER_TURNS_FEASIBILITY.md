# 用预生成的脚本化用户轮次替代活的 user-simulator LLM：可行性分析（草案 v0.1，2026-08-30）

本文件是继 `LLM_LATENT_STATE_FEASIBILITY.md`（隐状态替代 z_t）之后的另一条降成本备选方向的
可行性记录，回答的问题是：`selfchat.py::run_trajectory` 里每轮都要调用一次活的
`user_sim.generate()`（模拟用户），这部分生成能不能用离线预生成好的固定脚本替代，从而省掉
每条轨迹里这一部分的生成开销。**本文件仅做分析记录，不修改 `persona_drift_control/` 已有
代码**，与 `LLM_LATENT_STATE_FEASIBILITY.md` 的定位一致：先想清楚设计和代价，再决定是否实施。

## 1. 结论摘要

- 技术上可行，但**省下的成本比直觉上小**：当前每轮真实生成次数是 1 次用户 + 1 次主线 + 4 次
  探针 = 6 次（`probe_repeats` 默认 4），脚本化用户只能省掉其中 1 次，边际收益约 17%，而不是
  "砍一半"——那个更大的收益只有在探针也被去掉（`LLM_LATENT_STATE_FEASIBILITY.md` 方案，本次
  未采用）之后，用户轮次才在剩下的 2 次生成里占一半。这个数字上的区分需要在决定要不要做之前
  先说清楚，避免预期落空。
- 除了生成次数，还有一块容易被忽略但真实存在的成本：**不需要再加载第二个模型**。
  `screening.py` 里 `agent`/`user_sim` 是两个独立加载到 GPU 的 `ChatModel` 实例（各自的权重加载
  + 显存占用），脚本化之后 `user_sim` 这个模型完全不需要加载，省的是一次性的模型加载时间和显存，
  跟"每轮省一次生成"是两笔独立的账。
- 核心设计难点不是"要不要脚本化"，而是**脚本内容从哪来、怎么保持自然度**：现有代码里用户的
  下一句依赖上一轮 agent 的真实回复（`user_history.append({"role": "user", "content":
  agent_text})`），脚本化必然打断这个"用户听到 agent 说了什么再回应"的反馈闭环。直接手写模板
  句子会引入和"方案2"（language_constraints 无探针）同样的"审稿人质疑人为捏造"的风险，需要
  用离线一次性 LLM 生成的自然语料库代替手写模板，而不是走模板路线。
- 建议：作为**方法学/工程验证工具**先做小规模验证（脚本化 vs 活的 user_sim 跑同一批
  system prompt/seed/condition，对比 y_probe 轨迹是否一致），而不是直接替换进正式采集协议；
  即使验证通过，也建议保留一个"活用户"的小样本子集用于最终结果的可信度背书，而不是全量静默替换。

## 2. 背景：现状 vs 提案

| | 现状（`selfchat.py::run_trajectory`） | 本文件提案 |
|---|---|---|
| 用户轮次来源 | 每轮实时调用 `user_sim.generate(user_history, seed=..., config=config.user_gen)`，依赖上一轮 agent 的真实回复 | 离线预生成的固定脚本，按 `(topic, seed)` 索引，运行时直接查表取第 `turn` 句 |
| 是否依赖 agent 当轮真实回复 | 是（`user_history` 里塞的是 agent 真实说的话） | 否，脚本在所有 trajectory 生成之前就已经写死，无法感知某条 trajectory 里 agent 具体说了什么 |
| 每轮生成次数 | 1（用户）+ 1（主线）+ 4（探针）= 6 | 0（用户，查表）+ 1（主线）+ 4（探针）= 5 |
| 需要加载的模型数 | 2（`agent` + `user_sim`，各自占显存/加载时间） | 1（只需 `agent`） |
| 与 `core.py`/现有协议接口的关系 | — | 只影响 `user_text` 的产生方式，`trajectories.jsonl` 表结构、`u_remind`/`y_probe` 等列完全不变 |

## 3. 用户脚本从哪来：为什么不能直接手写模板

`selfchat.py` 里 `USER_SYSTEM_PROMPT_TEMPLATE` 已经把用户限定成"围绕给定话题自然聊天、不提及
对方设定"的角色，这意味着用户轮次本身就被设计成与 agent 具体人格设定无关的**通用话题闲聊**——
这一点降低了"脚本化打断反馈闭环"这个问题的实际影响（用户本来就不该对 agent 的具体设定做出
针对性反应）。但即便如此，脚本内容如果是手写模板（"那你觉得{topic}怎么样？""我也这么想"之类），
会招致跟方案2完全一样的质疑：审稿人可以说"这不是真实对话分布，漂移/不漂移的结论无法推广到真实
使用场景"。

因此脚本库本身仍然应该用 `user_sim`（同一个 Qwen3-4B/8B）离线生成，只是**生成一次、复用多次**，
而不是每条 trajectory 都重新生成一次：

- **生成方式**：为每个话题（`TOPICS` 里 12 个）× 若干个 seed（建议覆盖协议规模用到的 seed 集合，
  如 4–8 个），离线跑一次 T=16 轮的用户独白/自聊，产出固定的 16 句用户话术，存成脚本库（例如
  `persona_drift_control/resources/user_scripts/<topic>__seed<seed>.json`）。
- **"听什么才能往下说"的替代方案**：离线生成时用户仍需要"听到"某种 agent 回复才能自然接话，
  但这时不能用真实的每条 trajectory 各自的 agent 回复（那样就退化成没省成本）。可行做法是固定
  用**一次参考对话**（任选一个 system prompt/seed 跑一次真实的 agent+user 自聊，只取里面 agent
  说的话作为"参考回复"喂给离线用户生成），生成出的脚本之后被复用到所有其他 system
  prompt/seed/condition 组合上——这本质上和同事那 8 个数据集"输入由模板决定、不再实时生成"的
  做法是同一类工程取舍，不是本项目独有的问题。
- **多样性 vs 成本的权衡**：若每个话题只生成 1 份脚本，会导致同一话题下所有 trajectory 的用户
  轮次逐字相同，这本身就是一种新的人为规律，可能被质疑"用户轮次不够多样、可能是漂移/不漂移的
  混淆变量"。建议按 seed 生成多份（比如 4–8 份/话题），用 `seed` 索引选脚本，让"脚本选择"本身
  也随 seed 变化，而不是所有 trajectory 共享同一份文本。

## 4. 工程改动点（均为增量设计，暂不实施）

- `selfchat.py::TrajectoryConfig` 新增字段 `user_mode: Literal["live", "scripted"] = "live"`，
  默认值保持现状不变，不影响已跑过的 screening 结果的可复现性。
- `run_trajectory()` 签名层面，`user_sim` 参数在 `user_mode == "scripted"` 时可以传 `None`；
  取 `user_text` 的那一行改成按 `user_mode` 分支：`live` 走现有 `user_sim.generate(...)`，
  `scripted` 走 `script[turn - 1]`（脚本来自新增的加载函数，例如
  `load_user_script(topic, seed) -> list[str]`，读 `resources/user_scripts/` 下的 JSON）。
- `screening.py`/正式采集入口：`user_mode == "scripted"` 时跳过 `ChatModel(user_model_id, ...)`
  的加载，省掉对应的显存和加载时间；`run_config`/日志里需要记录 `user_mode` 和脚本库版本，
  确保产出的 `trajectories.jsonl` 能追溯到具体用的是哪份脚本（脚本库本身也应该像
  `resources/PROVENANCE.md` 记录第三方探针题库那样，记录生成脚本库时用的 model_id/seed/参考对话）。
- 新增一个一次性的离线生成脚本（例如 `scripts/generate_user_scripts.py`），产出并落盘脚本库文件；
  这个脚本本身要跑一次真实生成（12 话题 × 若干 seed × 16 轮），但这笔成本只付一次，不随后续
  trajectory 数量线性增长——这是它相对"每条 trajectory 都活生成"的根本优势所在。
- `core.py`、`AugmentedKoopmanModel` 等 Koopman 建模代码完全不受影响，这个改动只发生在
  `selfchat.py` 的用户轮次生产环节，不改变 `trajectories.jsonl` 的表结构或下游建模接口。

## 5. 建议的验证顺序（先小规模对照，再决定要不要转正）

1. **一致性检验**：挑 3–5 个 (system_prompt, seed, condition) 组合，分别用 `live` 和
   `scripted` 各跑一次，对比逐轮 `y_probe` 轨迹（不要求逐字相同，但漂移趋势/`u_remind` 响应
   应该在噪声范围内一致）。如果两者系统性不一致（比如 scripted 模式下漂移消失或方向相反），
   说明"用户是否真实反应 agent 的话"这件事本身就是动力学里不可忽略的一部分，不能脚本化。
2. **多样性检验**：脚本库生成完之后，人工抽查几份同话题不同 seed 的脚本，确认不是退化成
   高度重复的文本（比如同一开场白+细微改写），避免脚本库本身引入新的人为规律。
3. **成本核算**：实测一次性生成脚本库的耗时（12 话题 × N seed × 16 轮的活生成），除以预期
   会跑的 trajectory 总数，确认摊薄后的边际成本确实低于继续用活 user_sim；如果正式采集规模
   不够大（比如只是本次 screening 这种 20 条量级），摊薄可能不划算，这条路线更适合正式
   320 条采集这种规模，而不是小规模 pilot 本身。

任一步不达标，都应该停在这里，继续用活的 `user_sim`，而不是直接把 `user_mode` 默认值改成
`scripted`。

## 6. 风险与局限

- **打断反馈闭环是真实的、非零的简化**：即使用户轮次被系统提示限定为"通用话题闲聊"，脚本化
  之后用户完全无法对某条具体 trajectory 里 agent 实际说了什么做出反应，这和真实部署场景（用户
  确实会看到并回应 agent 的话）存在系统性差异，需要在最终写文档/论文时明确声明这一限制，而不是
  含糊带过。
- **不应该完全替代活用户数据**：即使第 5 节的验证都通过，建议的做法是"大规模/多次重复的采集用
  scripted 省成本，但保留一个活用户的小样本子集"，用于交叉验证结果没有被脚本化引入的偏差——
  这也是为了回应"方案2"暴露出的同一类审稿人质疑（"这是不是为了省事而人为简化了任务"），预先
  留一个可以拿出来对比的活数据子集，比事后被要求补做更省事。
- **省下的成本量级有限**：第 1 节已经说明，只做这一项，边际收益约 17%（6 次生成/轮降到 5
  次），不是数量级的成本下降；如果目标是大幅缩短正式 320 条采集的墙钟时间，仍然需要配合
  `LLM_LATENT_STATE_FEASIBILITY.md` 或探针本身的精简（本次讨论中判断风险较大、未采用），
  单独做这一项能省的时间有限，需要管理预期。
