\subsection{Experimental Setup}
\label{sec:exp_setup}

Experiments cover two task groups.
The first is self-built multi-turn tasks that form the modeling line.  % RECOVERED 2026-09-19 (Opus); semantic.md Experiments P1
Table~\ref{tab:prediction} carries seven of them: sentence length, Joint-3, Joint-2, sentiment, defense, constraint and CEFR.  % tab_prediction.tex column headers, updated 2026-09-20 (Items (s1)/(s2) renamed)
Joint-2 tracks two attributes of one sentence at once, word count and average word length; Joint-3 adds comma count. The other five tasks track a single attribute.
Each task is a set of prompts, called items; every item is run for several turns and yields one trajectory.  % item defined here 2026-09-22 (terminology_fix_plan #14); DATASETS.md  % configs/dataset/vector_count_stage1_t10.yaml, vector_count_stage2_t10.yaml; DATASETS.md
Appendix~\ref{app:A2_small_columns} carries the four small-sample columns, sentiment and defense again plus average word length and GSM8K-sharded, with their sample-size caveat.  % _build_report.json:prediction_appendix
The second group is three public instruction-following benchmarks that form the control line: IFBench, IFEval and COLLIE.  % contract.yaml meta.benchmarks
Together they carry eleven subtasks: WC, UWC, NS and NP for IFBench; KF, WC, NS and NP for IFEval; Word, Sent. and Para. for COLLIE.  % contract.yaml meta.benchmarks
The modeling line runs on a single LLM, Qwen3-4B-Instruct-2507, which both produces and scores the self-built trajectories, so every number in Table~\ref{tab:prediction} comes from that one LLM. 
The control line is separate: it reports two frozen target models, Qwen3-4B and Qwen3-8B, produced in a separate pipeline whose protocol Appendix~\ref{app:A4_equal_cost} records.

The modeling line compares six predictors, the six rows of Table~\ref{tab:prediction}.  % tab_prediction.tex row count
Stateless is a memoryless null, Last-turn is a single-reading state, and Memory w/o command is a multi-turn state without the command term.
LSTM is a recurrent sequence baseline, and KOMPAS (learned lifting) and KOMPAS (linear) are the two operator variants.
KOMPAS (linear) uses the identity lifting of \S\ref{sec:model}, the reported instance throughout this paper.
Window length, horizon, row counts, trajectory counts and the bootstrap protocol vary by task and are tabulated in Appendix~\ref{app:A3_window}; every interval in \S\ref{sec:exp_prediction}--\S\ref{sec:exp_mechanism} is a paired bootstrap over trajectories.  % details moved to App. A3 on 2026-09-21 (page budget, item A3)

The control line compares four methods per frozen model, the four rows of Table~\ref{tab:control}: Base, TMPC, RE-Control and KOMPAS.  % tab_control.tex row count
Base applies no control.  % tab_control.tex Access column '--'
TMPC and RE-Control are white-box latent controllers that require activation access to the frozen model.  % tab_control.tex Access column
KOMPAS needs only the instruction it sends, marked black-box Access, since it never opens the model.  % tab_control.tex Access column

A predictor that never beats the best memoryless guess scores zero, and one that halves that guess's error scores one half.
We define the prediction skill score as \(\mathrm{Skill}_H = 1-\sum_{h=1}^{H}\ell_h\big/\sum_{h=1}^{H}\ell_h^{\mathrm{null}}\). Here \(\ell_h\) is the squared forecast error at horizon step \(h\) from \S\ref{sec:problem_modeling}, and \(\ell_h^{\mathrm{null}}\) is the same quantity for that memoryless guess.  % contract.yaml symbol_lattice s_ell s_ellnull; eq:skill inlined 2026-09-21 (item A4)
That guess is the Stateless row of Table~\ref{tab:prediction}, which therefore scores 0.000 by construction.
The score $\mathrm{Skill}_H$ is therefore the fraction of that null's horizon error which the operator removes.  % contract.yaml symbol_lattice s_skill
A score of zero means tied with that null; a negative score means worse than it.

The control-line metric is each benchmark's constraint-satisfaction score, a per-subtask percentage with no interval attached.  % numbers_benchmark.yaml unit field; the per-subtask satisfaction definition is TODO(data) below and must be written here before submission
